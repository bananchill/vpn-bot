# TASK-016: Срок действия конфига, продление подписки и уведомления

**Статус:** Ожидает апрува
**Приоритет:** Высокий
**Дата:** 2026-03-02

## Описание

Добавить три связанных механизма: установку `expiryTime` в 3x-ui при создании конфига и его
обновление при продлении подписки; умное продление (сдвиг от текущего `expires_at` при активной
подписке); фоновые уведомления пользователям за 3 дня до истечения и в момент истечения подписки.

## Что будет сделано

1. **Alembic-миграция** — добавить два булевых поля в таблицу `subscriptions`:
   `notified_3d` и `notified_expired`.

2. **Изменить модель `Subscription`** в `bot/db/models.py` — добавить два новых поля с
   `default=False`.

3. **Изменить `vpn_service.create_config`** — принять параметр `expires_at: datetime | None`;
   вычислить `expiry_time_ms = int(expires_at.timestamp() * 1000)` и подставить в поле
   `expiryTime` вместо `0` при создании клиента в 3x-ui. Если `expires_at is None` — оставить `0`.

4. **Изменить `subscription_service.activate`** — добавить логику продления:
   - Если у пользователя есть **активная** подписка — `starts_at = текущий expires_at`,
     `new_expires_at = текущий expires_at + 30 дней`.
   - Если подписка истекла или отсутствует — `starts_at = now`, `new_expires_at = now + 30 дней`.

5. **Добавить `subscription_service.sync_configs_expiry`** — новая функция, которая после
   активации/продления подписки обновляет `expiryTime` всех конфигов пользователя в 3x-ui
   через `xui.update_client(client_uuid, inbound_id, {..., "expiryTime": expiry_ms})`.
   Вызывается из `payment.py` после `activate()` и `activate_promo()`.

6. **Добавить методы в `SubscriptionRepository`**:
   - `get_expiring_soon(now, window_start, window_end)` — подписки, у которых `expires_at`
     попадает в интервал `[window_start, window_end]` и `notified_3d = False`.
   - `get_expired_unnotified(now)` — подписки, где `expires_at <= now` и
     `notified_expired = False`.
   - `mark_notified_3d(sub_id)` — установить `notified_3d = True`.
   - `mark_notified_expired(sub_id)` — установить `notified_expired = True`.

7. **Создать `bot/services/notification_service.py`** — функция
   `check_and_notify_expiring(bot, session_factory)`:
   - Открывает новую сессию через `session_factory`.
   - Выбирает подписки с истекающим через 3 дня сроком (окно: `[now+2d23h, now+3d]`) и
     флагом `notified_3d = False` — отправляет уведомление, ставит `notified_3d = True`.
   - Выбирает подписки с `expires_at <= now` и `notified_expired = False` — отправляет
     уведомление, ставит `notified_expired = True`.
   - Каждое уведомление отправляется через `bot.send_message(telegram_id, text, reply_markup=...)`.
   - При ошибке отправки конкретному пользователю — логирует и продолжает (не прерывает цикл).

8. **Создать `bot/scheduler.py`** — инициализация APScheduler (`AsyncIOScheduler`),
   добавление задачи `check_and_notify_expiring` с интервалом 1 час (cron или interval).
   Экспортировать `scheduler` и `setup_scheduler(bot, session_factory)`.

9. **Изменить `bot/__main__.py`** — вызвать `setup_scheduler(bot, session_factory)` и
   `scheduler.start()` перед `dp.start_polling(bot)`. При завершении — `scheduler.shutdown()`.

10. **Добавить зависимость `apscheduler`** в `pyproject.toml`.

## Технические решения

### Передача expiryTime в 3x-ui
Сигнатура `create_config` расширяется параметром `expires_at: datetime | None = None`.
В хендлере `config.py` при вызове `create_config` передаётся
`subscription.expires_at` из активной подписки (которая к этому моменту уже проверена).
Формула: `int(expires_at.timestamp() * 1000)` — Unix timestamp в миллисекундах.
Значение `0` в 3x-ui означает "без ограничения", поэтому при `None` передаём `0`.

### Обновление expiryTime при продлении
После активации подписки из `payment.py` вызывается `sync_configs_expiry(user_id, new_expires_at, xui, session)`.
Функция получает все конфиги пользователя через `ConfigRepository(session).get_by_user(user_id)`,
затем для каждого вызывает `xui.update_client(client_uuid, inbound_id, full_client_settings)`.

Проблема: `update_client` требует полный набор настроек клиента, не только `expiryTime`.
Решение: получить текущие настройки клиента через `xui.get_inbound(inbound_id)`, найти нужного
клиента по `client_uuid` в поле `settings.clients`, обновить только `expiryTime` и отправить
обратно. Если получить настройки не удаётся (клиент удалён из панели) — логировать и пропустить.

### Деактивация конфигов при истечении подписки
`expiryTime` в 3x-ui **автоматически блокирует доступ** по истечению срока — клиент с
просроченным `expiryTime` не может подключиться к VPN. Дополнительная деактивация через
`enable=False` не нужна. Уведомление пользователю отправляется, но конфиги принудительно
не отключаются через API.

### APScheduler
Используется `apscheduler>=3.10` с `AsyncIOScheduler` и `IntervalTrigger(hours=1)`.
Scheduler стартует после инициализации бота, останавливается при `on_shutdown`.
В `bot/scheduler.py` хранится единственный экземпляр `scheduler` (singleton на уровне модуля).

### Окно "за 3 дня"
Задача запускается каждый час. Чтобы не пропустить пользователей и не дублировать:
- Выбираем подписки с `expires_at` в интервале `(now + 2d23h, now + 3d1h]` — окно ±1 час от
  72-часовой отметки.
- Флаг `notified_3d = False` гарантирует отсутствие дублей.

### Кнопка в уведомлениях
Оба уведомления содержат инлайн-кнопку "Продлить подписку", которая ведёт на `callback_data`
существующего `show_payment_menu` из `payment.py` (callback `"pay:menu"`).

## Критерии приёмки

- [ ] При создании конфига поле `expiryTime` в 3x-ui заполняется значением `expires_at * 1000`
      (если подписка активна), а не `0`
- [ ] При создании конфига без активной подписки (admin) `expiryTime = 0`
- [ ] При продлении активной подписки новый `expires_at = старый expires_at + 30 дней`
- [ ] При оплате при истёкшей подписке `expires_at = now + 30 дней`
- [ ] После продления подписки `expiryTime` всех конфигов пользователя обновляется в 3x-ui
- [ ] Scheduler запускается вместе с ботом и выполняется раз в час
- [ ] За 3 дня до истечения пользователь получает уведомление с кнопкой "Продлить"
- [ ] В день истечения (или после) пользователь получает уведомление с кнопкой "Продлить"
- [ ] Уведомления не дублируются: повторный запуск scheduler не отправляет уведомление дважды
- [ ] При ошибке отправки уведомления боту (пользователь заблокировал бота) — задача продолжает работу
- [ ] Миграция добавляет `notified_3d` и `notified_expired` без ошибок
- [ ] Тесты покрывают: логику продления `activate`, `sync_configs_expiry`, оба ветвления
      `check_and_notify_expiring` (3d и expired), дедупликацию уведомлений

## Вне скоупа

- Отключение (`enable=False`) конфигов в 3x-ui при истечении подписки — `expiryTime` сам
  блокирует доступ
- Повторные уведомления (например, каждый день после истечения) — только один раз
- Настройка интервала уведомлений через конфиг (хардкод: 3 дня и 0 дней)
- Веб-хук вместо polling для APScheduler
- Уведомления для admins (admins не имеют подписки)
- История уведомлений в БД (только флаги в таблице `subscriptions`)
- Уведомление за 7 дней или за 1 день — только за 3 дня

## Уточнения от заказчика

1. Кнопка "Продлить подписку" в уведомлениях — **открывает меню оплаты** (`callback_data="pay:menu"`).
2. Погрешность уведомления за 3 дня ±1 час — **приемлемо**.
3. При недоступности 3x-ui при обновлении `expiryTime`:
   - **Немедленно** сообщить пользователю: "⏳ Конфиги обновляются, это займёт немного времени."
   - Сохранить в БД флаг `configs_sync_pending = True` на записи подписки.
   - Scheduler (раз в час) повторяет попытку для всех подписок с `configs_sync_pending = True`.
   - После успешного обновления — `configs_sync_pending = False`.
